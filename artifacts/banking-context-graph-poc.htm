Core hypothesis

What this MVP proves

One falsifiable claim. Three query types that pure vector search cannot answer. If the graph answers these reliably and vector search cannot, the concept is validated.

Hypothesis
A graph-based context layer enables relationship-based retrieval that semantic similarity search cannot produce — answering questions about ownership, cross-team process chains, and access permissions without keyword matching or manual curation.
Find documents owned by the team responsible for trade settlement — not documents that mention trade settlement
Show what a person can access about the KYC process, filtered by their actual permission edges
Trace the full handoff chain from Sales to Operations for client onboarding — a relationship query, not a text query
What is not in this MVP

Regulation, Control, Risk, Client, Product, Case, Incident, Decision, and Project nodes are all excluded. Client Support and Tech Support team profiles are excluded. The regulatory compliance sub-graph, ingestion pipelines, and hybrid vector-graph retrieval fusion are all Phase 1 work — not MVP work. The MVP uses hand-loaded data, not automated connectors.

Why :System matters even in the MVP

The :System node is the one place to invest care now, even for a 3-day build. Every system node you create — CRM, core banking, trading platform — becomes the anchor for Phase 2 code repositories. Capture tier and criticality as properties from the start; retrofitting them is tedious. Everything else can be minimal.

Graph schema

6 relationship types

Six edges are enough to prove the hypothesis. Each one is included because it enables at least one proof query that vector search cannot answer. No edge is included for completeness alone.

The one edge that proves the concept

The HANDOFF_TO edge between Sales and Operations — with process: 'Client Onboarding' stored as an edge property — is the single relationship that demonstrates graph-native retrieval. A query asking "who takes over from Sales after KYC is complete?" traverses this edge and returns Operations instantly. No vector search can answer this from document similarity alone.

Validation

3 proof queries

Run these three queries against the MVP graph. Then run the same questions through a keyword search and a pure vector search. The delta is the POC result.

1Find documents owned by the team responsible for trade settlement
✦ Proves ownership traversal — vector search returns documents that mention settlement, not documents owned by the team that runs it
Cypher
MATCH (t:Team)-[:OWNS]->(p:Process) WHERE p.name CONTAINS 'Settlement' MATCH (t)-[:OWNS]->(d:Document) RETURN t.name AS owning_team, d.title AS document, d.type AS doc_type ORDER BY d.type
2What can this person access about the KYC process?
✦ Proves permission-filtered retrieval — returns only documents the person has a CAN_READ edge to, not all KYC documents in the corpus
Cypher
MATCH (person:Person {name: $user_name}) -[:CAN_READ]->(d:Document) -[:REFERENCES]->(p:Process) WHERE p.name CONTAINS 'KYC' RETURN d.title AS document, d.classification AS access_level, p.name AS related_process ORDER BY d.classification
3Trace the full handoff chain from Sales — who takes over at each step?
✦ Proves cross-team relationship traversal — this is a structural query about process ownership, not a content similarity question
Cypher
MATCH (start:Team {name: 'Sales'}) -[h:HANDOFF_TO]->(next:Team) OPTIONAL MATCH (next)-[:OWNS]->(p:Process) RETURN start.name AS from_team, h.process AS handoff_trigger, next.name AS to_team, collect(p.name) AS processes_owned -- Returns: Sales → 'Client Onboarding' → Operations → [Account Setup, Trade Execution...]
Measuring the result

For each query, run the equivalent natural language question through keyword search and pure vector search on the same document corpus. Score each result set: did the correct team/document/person appear in the top 5 results? The graph should score significantly higher on queries 1 and 3. Query 2 (permission filtering) is a hard failure case for vector search — it has no access model.

Build plan

3–5 day build checklist

Strictly sequenced. Each step produces something demonstrable before the next begins. Stop after step 6 and run the proof queries — that is the MVP deliverable.

  • 1 Open Neo4j Desktop. Create Team nodes for Sales and Operations. Create 5–8 Person nodes per team. Wire MEMBER_OF and LEADS edges. This is your organisational backbone — takes 2–3 hours maximum. Day 1 · AM
  • 2 Create System nodes for the 5–8 primary systems used by both teams (CRM, core banking, trading platform, settlement platform, KYC tool). Add USES edges from each team to its systems. Set tier and criticality properties — these persist into Phase 2. Day 1 · PM
  • 3 Create 3–4 Process nodes per team. Add OWNS edges from each team to its processes. Add RUNS_ON edges from processes to the systems they execute on. Wire the single HANDOFF_TO edge from Sales to Operations with process: 'Client Onboarding' as the edge property. Day 2 · AM
  • 4 Hand-pick 50–100 representative documents from your real document corpus. Export as CSV from Confluence or SharePoint. Load into Neo4j using LOAD CSV. Add OWNS edges from teams to their documents. Add REFERENCES edges from documents to the processes and systems they mention — use a simple keyword pass, not full NLP. Day 2–3
  • 5 Add CAN_READ permission edges. For each person, determine which documents they can access based on their team membership and document classification. Wire these edges. Even simplified permission rules (team members can read all team-owned documents) are sufficient to prove the permission filtering proof query. Day 3–4
  • 6 Run the 3 proof queries against the graph. Run the same questions through keyword search and pure vector search against the same document set. Record results. This comparison is the MVP deliverable — the graph should answer queries 1 and 3 correctly where vector search cannot, and query 2 is unanswerable by vector search entirely. Day 4–5
Definition of done

The MVP is complete when you can demonstrate — with real documents and real query results — that the three proof queries return correct, explainable answers from the graph, and that keyword search and pure vector search either fail or return lower-quality results on the same questions. That comparison is the business case for Phase 1.
